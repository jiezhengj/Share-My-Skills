# 参考样例

这些例子用于验证 Skill 的编辑方向，不是可以直接套用的句式。

## 例一：写作前只有主题

用户输入：

```text
我想写一篇关于 Agent 写长任务的文章。
```

错误处理：直接生成“背景—优势—挑战—未来”的完整文章。

正确处理：先询问目标读者、真实经历、中心判断和希望读者做什么；如果用户没有案例，就把案例标记为 `UNKNOWN`。

## 例二：有真实转折的个人文章

素材：

```text
我原来让 Agent 一次性处理很多重复任务。后来发现它开始自行改写输入条件，结果需要重新核对。
```

结构可以从“原来的做法—发现偏移—改成确定性脚本—仍需人工判断的地方”形成，而不必拆成“效率、创新、风险”三点。

## 例三：正式报告

正式报告中使用表格、定义和编号不代表 AI 味儿。应优先检查事实、来源、口径和术语一致性，不要为了降低模板感而删除必要结构。

## 例四：用户明确要求脱敏时的技术复盘

```text
真实项目名 → 某个桌面工具
真实模块名 → 配置模块
真实设备名 → 设备 A / 设备 B
```

保留“设备 A 拔出后仍读取 profile-a”这类动作和结果，但不要增加原始材料中没有的日志、截图或数字。

## 例五：已经自然的文章

如果文章事实具体、判断清楚、语言有作者习惯，即使存在“首先”或结构清楚，也应选择 `L0` 或 `L1`。不要因为 Skill 被触发，就强行重写。

## 例六：功能性事实替代抽象评价（正例）

抽象句“这个过程显著提升了效率”，如果作者提供了规模、流程、失败条件和责任主体，改写应落到它们上，而不是补“当时我很兴奋”。功能性事实（谁、做了多久、什么结果、什么没有生效）让读者能判断真假；材料不足时标记 `UNKNOWN`，不补写。

## 例七：氛围性细节冒充事实（反例）

“我盯着屏幕，看它一遍又一遍地跑，心里越来越凉”——没有功能性事实（跑了多久、谁在什么情况下中止、成本多少），只有氛围。这类细节不能替代“Agent 跑了将近 24 小时，我手动中止了它”这种可核验的事实。细节只承担氛围、不携带新信息时，应回到作者材料补功能性事实，或标记 `UNKNOWN`。
