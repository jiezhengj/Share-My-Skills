# 判断轨迹与过程收口

本文件用于处理个人经历、项目复盘、方法复盘和流程叙事中的一种普遍缺口：文章只留下“问题—结论”，却没有让读者看见人是怎样理解、行动、遇到阻碍并改变态度的。Agent、Goal、Workflow 和自动化系统只是其中比较容易暴露这个问题的例子。

## 何时启用

当文章核心在讲以下内容时启用：

- 作者或参与者在不确定情况下如何理解、选择和修正判断；
- 一段实践怎样产生一个方法、原则或新的工作方式；
- 一个项目、流程或尝试为什么继续、为什么转向或为什么停止；
- 局部结果为什么看起来不错，却没有改变整体判断或交付结果。

纯技术文档、纯观点文、产品说明或只报告最终结果的文章，不因出现“过程”“工具”或“Agent”等词而启用本文件。触发依据是文章是否需要呈现认识和行动的变化，而不是主题关键词。

## 路由示例

用文章承担的任务判断，不用关键词判断：

| 材料形态 | `trajectory_mode` | 处理方式 |
| --- | --- | --- |
| “配置项如下，执行这些命令后应得到以下输出。” | `SKIP` | 保持说明书的目标、步骤和验收，不补作者认识过程。 |
| “原本以为某种做法足够，实际执行后发现一个阻碍，后来改变了判断。” | `ENABLE` | 恢复预期、行动、阻碍、后果和判断变化。 |
| “一个团队在一项长期任务中反复修订，最后发现问题不在细节而在缺少收口标准。” | `ENABLE` | 即使没有 Agent，也检查局部结果、整体推进、成本和停止或转向。 |

只有材料中确实存在认识或行动的变化，才使用 `ENABLE`。不要因为文章里出现“工具”“流程”“复盘”或“Agent”就自动开启。

## 过程记录

启用后，不要只记录“问题—结论”。先建立判断轨迹：

```text
原本的预期 → 采取的行动 → 观察到的结果 → 局部成功 → 整体是否推进 → 时间/资源成本 → 停止动作 → 判断变化
```

判断变化必须是真实发生过的。如果认识一开始就清楚（来自文档、官方来源或前置知识），不得用“回头看”“后来才意识到”包装成顿悟；判断轨迹记录真实的预期与变化，不事后编造认识弧线。

其中“局部成功”和“整体推进”必须分开：

- 某一步做对了，不等于整体状态改善；
- 发现了新问题，不等于文章、方案或任务质量提高；
- 修改了很多内容，不等于结构性问题被解决；
- 找不到明显错误，不等于已经达到结束条件。

阶段标签也不等于判断轨迹。项目文章连续写“第一轮、第二轮、第三轮”，只能说明时间顺序；每个主要阶段还需要一个来源明确的对象、动作、观察结果或判断变化。若段落只留下阶段状态、工具清单和成果归纳，应标记为“项目履历化/报告化”，而不是把它误判成叙述已经完整。

## 假成功与没有收口

把以下情况作为候选问题，而不是直接下结论：

- 每轮检查都能找到一个新的、不能轻易说错的问题；
- 每轮修订都有局部理由，但整体指标、读者判断或交付结果没有明显变化；
- 执行者持续消耗时间、token 或注意力，却没有新的停止依据；
- 把“没有明显错误”或“每一步都能解释”当作“工作取得进展”；
- 任务没有二级化的收口标准，只能不断寻找更细的改进点。

需要写清楚：作者为什么一开始认为继续是合理的，什么结果让作者意识到继续没有带来结构性变化，谁或什么动作让过程停下来，以及停止时仍然留下什么未知项。

## 成本和停止

时间、token、人工复核、机会成本或必须中止的动作，只在材料明确提供时写入。不要凭空增加“浪费了很多资源”之类的评价。

停止事件可以是：

- 达到预先写好的验收条件；
- 明确失败并回滚；
- 触发外部阻塞，记录为 `BLOCKED`；
- 发现继续工作不会改变结构性结果，手动中止并记录 `UNKNOWN`；
- 作者或相关人确认当前结果足够，结束本轮。

“停止”不是天然成功。文章要区分停止原因、当前结果和未解决问题。

## 写作和冷读验收

陌生读者应该能够回答：

1. 任务一开始为什么看起来值得继续？
2. 哪些动作只是局部成功，为什么没有带来整体推进？
3. 付出了什么成本，谁在什么时候决定停止？
4. 停止后得到的判断是什么，还有哪些内容不能确定？

如果文章只剩“Agent 会死循环，所以要设置停止条件”，但读者不知道循环如何发生、为什么难以判错、为什么最后要停，说明过程轨迹没有写出来。
