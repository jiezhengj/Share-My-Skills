# 作者声音与具体性

用途：保留作者的判断、经验、犹豫和文体；不把自然化理解成统一口语化。

适用模式：`prewrite`、`drafting`、`rewrite`、`cold-read`。

## 保留什么

- 作者实际使用过的第一人称、术语、短句和表达习惯；
- 作者的犹豫、限制、取舍和不确定性；
- 具体动作、异常情况、时间成本、失败和后果；
- 作者愿意承担的判断，而不是模型替作者生成的平衡结论。

## 检查什么

- 改写后是否仍然像作者，而不是像统一的网络口语；
- 口语连接词是否匹配作者自己的用语习惯（如“坦白讲”“说真的”），而不是被替换成“说白了”“其实”这类 AI 高频词；
- 是否把“我在这个场景里观察到”改成了普遍规律；
- 是否把犹豫改成过度肯定；
- 是否删掉了必要的专业表达；
- 是否为了“有温度”增加了作者没有说过的情绪；
- 所谓具体细节是否真的改变了读者理解，而不是只增加地名和形容词。

## 原话与改写的来源回归

作者明确使用的专业术语、概念词、比喻、短语和带限定的判断，不能因为它们凝缩、正式或“听起来像模型”就被判为 AI 表达或擅自替换。改写前逐项对照 `source-map`：

- 保留作者原话的来源权限，即使它不够口语；
- 保留能体现作者取舍、判断强度和不确定性的限定词；
- 不把精确事实无理由改成模糊说法，例如把明确天数改成“十几天”；
- 不把不自然的模型转述当成作者原话，也不把作者原话归因给模型；
- 发现原意、主体、时间或责任发生漂移时，优先回到原始材料修复。

“像 AI”只能描述读者体验，不能倒推词语来源或作者身份。来源判断和文体判断必须分开记录。

## 第一人称的功能

第一人称本身不是 AI 味儿。逐句判断它承担的功能：

| 类型 | 例子 | 处理方式 |
| --- | --- | --- |
| 事实证据 | “我打开日志，看到设备 ID 已经变了” | 保留，必要时补足动作和结果 |
| 作者判断 | “我当时以为构建通过就够了” | 保留，它说明判断如何改变 |
| 责任或来源 | “我问了 Codex” | 通常保留，交代信息从哪里来 |
| 叙述支架 | “我先想到的是”“我觉得最容易忽略的是”“我现在会这样写” | 改成直接的事件、判断或方法 |

检查连续段落是否都用“我”开头，检查删掉某个“我”后是否损失了事实、判断或责任。如果没有损失，它很可能只是作者标签，不是作者声音。

## 读者姿态：写作的起点，不是事后补丁

写作时心里先有一个假想读者，想象在对读者说话，带一点“推销观点”的姿态（不是极端意义的推销，而是有意识地让读者接受你的判断）。这样写出来的句子天然有明确主体，自然会出现“大家”“我们”“你”“如果你也”“我想和大家说”“现在不能再怎么怎么”“大家现在要怎么怎么”“我建议你试试怎么怎么”。

不要“先写带‘我’的句子，再删‘我’，再补主体”——那只会留下补丁痕迹。句子没有明确主体时，问题不在“我”太多，而在作者心里没有读者。与其事后补主语，不如重写句子，让它对读者说话。

示范（备忘录式 → 对读者说话）：

- “这两个项目下来，现在不只问方案写得够不够详细” → “这两个项目下来，我想和大家说，如果你也和我一样在尝试把 goal 用到任务里，不要只问方案写得够不够详细”
- “这件事也提醒了一点” → “这件事也提醒了我们一点”

## 安全改写

优先把抽象评价改成作者提供的主体、动作、结果和限制：

```text
“这很重要” → 谁在什么情况下遇到了什么后果？
“效率显著提升” → 用了什么流程，观察到了什么变化，有什么失败条件？
“值得推广” → 适用于什么场景，不适用于什么场景？
```

如果作者没有提供答案，提问或保留 `UNKNOWN`。不要用“某用户”“某企业”补齐文章。
