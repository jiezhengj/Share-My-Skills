# 思维形态观察样本

用途:作为 `human-narrative-shape.md` 八个维度的观察来源。样本来自作者在对话框里的随手叙述,不是正式写作。

## 边界

- **对话,非写作**;
- 只用于观察人类如何处理真实材料(情绪、细节、判断、责任、命名、升华),不用于判断成稿是否像人;
- 不得要求成稿具备对话特征(口语、第二人称、未展开指涉、句法粗糙);
- 本文只作形态对照,不作为"应该长什么样"的写作标准。

## 来源权限

- 作者真实对话文本;
- 保留原样,不做规范化或润色;
- 仅用于技能内部的形态对照与回归说明。

## 样本原文

> 其实之前我做了一个比较大的项目,也用了几次 goal 模式。
>
> 那个项目,是一个产品需求和原型梳理的项目。我接手了一个不复杂的产品,主要就是小程序和运营后台两个端,其线上 1.0 版本想升级到 2.0。从业务角度,1.0 并未真正投入运营,2.0 也没有明确的运营计划和资源筹划,但和很多不专业的公司和老板一样,老板经常会认为一切的发动机是产品,要先把产品推上去,并且因为公司没有自己的技术团队,更加要用瀑布流的方式在一个大版本里堆积超级大量的需求。且因为老板不专业,所以大多数需求都是拍脑袋的一句话需求,无有优先级,不允许取舍,不允许砍需求,大量的主观感受,导致在我来之前的接近 2 个季度,2.0 长期停留在需求阶段,产品经理和产品运营流动性极大,换了好几任人,最后我拿到手的素材仅有 1.0 的源代码、上上任产品留下的非常混乱的 Axure RP 文件(里面是一些线框图和一些备注),以及上一任产品留下的 Figma 文件(他在职 15 天仅仅是试图把线框图换个工具重新画一遍,里面依然是一些语焉不详的备注),称不上是真正的产品需求,这些图里还有大量模糊、冲突、矛盾的地方。而老板也已经失去耐心,几乎约不到人,在职的也没有真正的产品运营了,很多模糊、冲突、矛盾并不知道是不是冻结的决策、是谁的决策、或者谁能做决策。我选择了借助 Codex 来完成产品需求梳理。
>
> 我先建立了一个科学的产品需求文档群的框架,并且通过 AGENTS.md 、README、指南、台账、变更记录等多个项目规则进行了防御性的约束,确保每个模糊项都能做全面查证、每个新决策都能全面落到相关的文档去。
>
> 第一轮,我就用了 goal 模式,让 Agent 理解和整合 Axure RP 和 Figma,并参考 1.0 源代码,把需求以我的框架梳理出一版产品需求,过程中它有自行思考和决策的权力,但决策都需要记录决策依据。最后再生成一个小程序用户视角的完整的用户故事。
>
> 第二轮,我和 Agent 结对,针对用户故事逐项厘清模糊、作出决策,对其上一轮的一些错误决策作为拨乱反正。这个过程中,因为缺少业务方的一手信息输入,很多决策是基于我的运营经验和业务理解去做的。过程中,每个决策,都会转化为多个写入点,写入到对应的需求文档里。到这里,这个仓库已经成了一个关于本期项目的完整的知识库,里面既有基线素材、也有落盘的文档和决策,也有完整的决策记录,甚至还包含了我的业务思维,相当于整体做了一个蒸馏,到此,很多问题问这个知识库和问我本人,是差不多等效的。
>
> 第三轮,也是一个 goal,完成第二轮后,我试着让 Agent 前后对照所有的已落盘需求,进行查漏补缺。本来以为经过了前两轮后,这一轮已经有了大量的落盘需求作为基座,而且我有极强的规则作为边界、防止模型逸出,应该是个确定性很强的工作。但实际上,Agent 跑了快 24 小时依然没有停下来的迹象,它永远能发现一个新的具体的冲突点并去解决,你也很难说它是错的。最后我不得不手动中止了这个 goal 的循环。而后,我再试图让 Agent 通过需求文档去建立 html 原型时,发现这 24 小时的查漏补缺并没有从结构性上真正提高多少需求文档的质量,相当于 24 小时都是白跑的。打个比方,很像你是一个编辑,让一个实习生对一篇文章的前后逻辑、语义去进行检查和修订,他忙了 24 小时,看似修订了很多,也不算有错,但大多数可能是一些细枝末节的问题。所以我意识到,也许未来模型的智能水平再提高后,此类任务的表现会更好;但在当下,goal 模式哪怕你的基准数据已经完备、给的指令也看似清晰,但只要它不是明确量化、有二级化的收口标准的目标,它就不适合 goal 模式。
>
> 再扩展开来,我现在仅仅是在一个成熟的 Agent 框架内执行任务。但如果我自己设计一个或一组 Agent 去完成任务,在 Loop 层面,通过事件驱动,感知-推理-规划-执行-观察-评估 这个链路里,非常容易出现这种"假成功",就是每一轮工具调用都成功、事件驱动也成功、消耗大量的时间和 token,但其实进入了死循环。
>
> 后来,在这篇文章里写的另一个项目里,同样准备用 goal 模式,我就格外注意这个点,并得到了印证。

## 样本观察(与八个维度的对应)

- **情绪在场方式**:连用三个"不允许,不允许,不允许";"相当于 24 小时都是白跑的"——选词与节奏承载情绪,无情绪名词。
- **细节类型**:"他在职 15 天仅仅是试图把线框图换个工具重新画一遍"——功能性事实(谁、多久、意外结果)。
- **判断形态**:"也许未来模型的智能水平再提高后,此类任务的表现会更好;但在当下……""并不知道是不是冻结的决策、是谁的决策、或者谁能做决策"——留后路,承认信息不完整。
- **责任归属**:"上上任产品""上一任产品""老板不专业""产品经理和产品运营流动性极大,换了好几任人"——责任具体到人。
- **命名密度**:描述"假成功"现象("非常容易出现这种'假成功',就是……"),但不做加粗命名,不建立概念体系。
- **升华密度**:讲到"我就格外注意这个点,并得到了印证"就停,不总结陈词。
- **否定对仗**:全篇无"不是……而是……"成串。
- **文本对话性**:"你""你的基准数据""在这篇文章里写的另一个项目里"——对具体听者,这是对话属性,不是写作参照。写作场景不得据此要求成稿有对话感。

## 随笔类写作样本参照（《关于 AI 的碎碎念》）

作者另有随笔类写作样本，确认为作者本人撰写，不属于 AI 生成。它与对话框人话类型不同：对话样本观察"作者如何处理真实材料"，随笔样本参照"作者的写作判断方式"。

- 来源：作者本地随笔库中的《关于 AI 的碎碎念》系列（2026 年各月）；运行环境不要求该路径存在。
- 特征：判断直接、口语连接、具体案例撑判断、敢于点名但不夸大、结尾停在判断不升华
- 类型局限：碎片化随笔，无成文结构、无读者导向组织；不能作为"成文类文章"的正例
- 用途：判断作者声音时的文风参照——吸收其判断力与具体性，不模仿碎片化形态
