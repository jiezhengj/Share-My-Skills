# 文章类型路由

先判断文章类型，再选择结构和自然化标准。不要把所有文章都改成聊天口吻。

| 类型 | 读者主要问题 | 优先关注 | 不要做 |
| --- | --- | --- | --- |
| 个人经历 | 发生了什么，能借鉴什么 | 起点、转折、行动、结果、限制 | 把个人经验写成普遍规律 |
| 观点文章 | 作者具体主张什么 | 证据、反例、取舍、责任 | 用“客观全面”回避判断 |
| 方法文章 | 读者怎样处理问题 | 步骤、前提、停止标准、例外 | 只列清单不解释原因 |
| 工具介绍 | 是否值得用，怎样开始 | 痛点、输入、过程、输出、限制 | 只做功能罗列 |
| 技术文章 | 方案为什么成立 | 术语、机制、测试、失败条件 | 为了口语化删除必要定义 |
| 正式报告 | 信息是否准确可追溯 | 来源、口径、时间、术语一致性 | 因“像 AI”而故意打乱结构 |

## 读者契约

开始写作或改写前，记录：

```text
目标读者：
读者遇到的具体问题：
文章准备给出的判断或帮助：
读者读完后的最小行动：
文章不承担的判断：
```

## 说明书和面向读者的文章

“技术文章”不等于“技术文档”。先判断交付对象：

- **说明书/技术文档**：读者需要快速查到定义、步骤、验收项或参数，可以直接从结论和规则开始；
- **面向读者的技术文章**：读者需要理解一个原本看似合理、后来暴露问题的判断，或理解作者为什么得出这个结论，需要组织一条理解路径。

面向读者的文章不必写成聊天，也不必虚构场景。它至少要让读者看见其中一种推进关系：

```text
原先看起来如何 → 在什么地方遇到阻碍 → 为什么原来的理解不够 → 后来如何判断或处理
```

如果素材没有真实事件，不补写经历；可以改用读者常见的疑问、一个反例、一个看似正确但不够用的写法，或一组前后对照来完成推进。

## 结构建议

- 个人经历：原来怎么做 → 遇到什么 → 哪个细节改变判断 → 后来怎么做 → 仍有限制；
- 观点文章：争议场景 → 中心判断 → 证据 → 反例 → 适用边界；
- 方法文章：常见错误 → 错误原因 → 正确步骤 → 具体例子 → 不适用情况；
- 技术文章：故障现象 → 错误模型 → 方案 → 验证 → 剩余风险。

这些只是候选结构。最终结构应由材料中的时间、冲突和因果关系决定。
