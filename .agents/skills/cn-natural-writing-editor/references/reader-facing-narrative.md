# 面向读者的理解路径

本文件处理一种常见问题：文章事实和结论都没有错，但写法像把技术文档压缩成了几段说明，读者看不到作者为什么这样判断。

## 一、这里的“故事性”是什么

这里的故事性不是虚构人物、增加对白或强行口语化，而是让读者看到理解如何推进。一个面向读者的技术文章，通常需要回答：

1. 读者原本会怎样理解这个问题？
2. 哪个现象、动作或反例让这种理解遇到阻碍？
3. 作者的判断为什么发生变化？
4. 后面的规则、方法或示例如何回答前面的疑问？

这条路径可以来自真实经历，也可以来自一个具体的读者问题。没有素材时，不编造“我当时”“用户后来”“现场发现”等经历。

## 不要把人的思考压平

去除 AI 味儿，重点不是把句子改得更口语，而是检查文章有没有把人的判断过程压平。活人的叙述通常会保留：当时为什么觉得某种理解合理、什么行动暴露了问题、为什么做出下一步选择、结果怎样改变了判断，以及哪些地方仍然不能确定。模型化的写法则容易直接从结论跳到方法，把每一步都写成进展，把不断发现问题写成不断完善，把不确定性整理成顺滑的总结。

这条判断适用于个人经历、项目复盘、方法文章和解释型文章，不要求文章必须讲故事，也不要求加入对白。即使是正式文体，也可以通过前提、阻碍、取舍、后果和适用边界，让读者复原“原来怎样理解，后来为什么改变”。纯技术文档则优先保证可查找和可执行，不强行添加认识过程。

读者视角也不是在文中频繁写“读者可能会问”。先判断读者在看到当前材料时最可能怎样理解，哪一个事实或反例会让这种理解遇到阻碍，下一段应该回答哪个具体疑问。读者代理只是必要时的表达手段，不是固定句式。

## 二、素材来源与关系权限

把不同来源分开处理，不允许资料之间互相制造事实：

| 材料 | 可以直接支持 | 不能直接推出 |
| --- | --- | --- |
| 作者原话或明确经历 | 作者做过什么、看到什么、怎么判断 | 原话没有写出的动作、环境、情绪和细节 |
| 外部文档或理论 | 定义、机制、公开事实和来源观点 | 作者本人接触过、相信过或亲历过这些内容 |
| 假设案例 | 标注为假设后帮助解释机制 | 真实用户、朋友、现场或结果 |
| 作者推断 | 标注为观察或推断后的判断 | 更具体的因果、数字或普遍规律 |

为每个重要段落画出关系：

```text
案例/观察 → 暴露的问题 → 概念或资料解释 → 判断变化 → 读者可以带走的做法
```

概念只是跟在案例后面，或案例只被用来装饰已经写好的规则，都算关系没有建立。没有足够材料时保留 `UNKNOWN`。

## 三、先判断文章交付方式

### 说明书或正式技术文档

允许直接写：目标、范围、步骤、参数、验收和风险。重点是可查找、可执行、可追溯，不要求增加故事性。

### 面向读者的技术文章

不能只把结论、规则和代码示例依次摆出来。至少补出一个真实存在的理解转折：

```text
看起来已经足够 → 放进实际场景后卡住 → 找到卡住的原因 → 给出更合适的写法
```

这里的“补出”是调整已有材料的顺序和解释，不是添加不存在的事实。

## 四、常见的说明书化段落

重点检查以下组合，而不是单独检查某个词：

- 前一段刚提出问题，下一句立刻用“所以”“因此”给出规范；
- 先宣布“应该怎么做”，再用代码块或清单补例子，但没有解释为什么这个例子重要；
- 把作者的认识过程压缩成“结论 → 不要这样 → 可以这样”；
- 每段都在回答“是什么”，却没有说明“原来为什么看起来合理”“在哪里失效”；
- 语言很顺，段落关系也正确，但读者无法复述判断改变的原因。

遇到这些信号，先判断素材中是否已有场景、阻碍、反例、提问或前后变化。没有就标记 `UNKNOWN`，不要靠润色补齐。

## 五、改写动作

根据素材选择最小动作：

1. 把读者熟悉的、看似合理的理解放到前面；
2. 写出实际执行或判断时出现的阻碍；
3. 说明阻碍暴露了哪个隐藏条件或范围问题；
4. 再给规则、方法或示例，并说明它解决前面的哪一个问题；
5. 保留限制，不把一次观察写成普遍规律。

在真正的摩擦点可以加入“读者代理”：读者可能提出的疑问、误解、反例或短暂停顿。它可以是一句解释或一个转折，不需要虚构对话，也不需要把文章改成聊天体。

例如，一段方法文如果直接写：

```text
所以，范围应该先收窄。
比如，不要写“完成整体升级”，可以写成……
```

先检查作者是否已经提供了“材料单独看起来完整，但进入实际执行后仍无法判断”的事实或观察。如果有，可以按以下逻辑重排：

```text
材料单独阅读时已经很完整 → 进入实际执行后仍然无法判断 → 问题在目标边界而不是材料长度 → 再给出范围收窄的例子
```

这只是结构示意，不是固定句式，也不要求写成口语。

## 六、冷读验收

把这一段交给不了解背景的读者，检查他能否回答：

- 这个目标为什么一开始看起来像是明确的？
- 执行者后来会在哪里卡住？
- 卡住说明原来的写法缺了什么？
- 后面的示例是在解决哪个具体问题？
- 哪个读者疑问或误解推动了下一段？

如果只能复述“目标要明确、范围要收窄”，但说不出为什么，说明文章仍然停留在说明书层面。不要用增加比喻、感叹或口语词来掩盖这个缺口。

## 七、开头锚点检查

面向读者的文章，前几段必须让读者建立：这篇文章在讲什么、核心概念是什么、为什么值得读。不能假设读者已有完整背景。

检查：

- 第一个动作用到的核心术语，读者第一次遇到时能否理解？
- 如果标题里的概念在开头第一段就被使用，前面是否先给了白话定义或直觉？
- 开头是否直接进入动作/术语，跳过了“这是什么”这一层？

“从具体进入”不等于“跳过背景”。先用一句白话把核心概念锚住，再进入具体故事。

定义之外，用读者已知的参照物建立连接。目标读者用 Codex、Claude Code，就先说“你们用的工具里就有”，再讲概念。参照物能拉近距离，抽象定义不能。这条适用于全文，不只是开头。

## 八、叙述姿态：对读者说话，而不是写备忘录

文章的作者是“对读者说话”，还是“写给自己看的备忘录/笔记”？这是读者视角、对话感、故事感、叙述感的根源。

### 备忘录姿态（AI 味来源）

- 无主语句子密集（删掉“我”后不补主体，像对自己说话）；
- 备忘录式“我会”陈述（主语是“我”、未来行动，自说自话）缺乏面向读者的指向；注意区分：客观机制/规律的“会”（主语是事物，如“Agent 会一直工作”）描述运行方式，是正常的，不在其列；
- 自说自话的过渡：“也得说清楚”“所以”“换句话说”，不承担“告诉读者什么”的功能；
- 不拉近距离：不解释读者需要的背景，不出现“大家”“我们”“你”。

### 读者姿态（拉近距离）

- 句子有明确主体；删掉“我”后无主语时，用“我们”“大家”或保留主语，避免备忘录化；
- “会”用在面向读者的指向：建议、预测、“现在不能再怎么怎么”“大家现在要怎么怎么”“我建议你试试怎么怎么”；
- 过渡词承担读者功能，或省略；
- 主动拉近距离：解释读者需要的背景（“大家常用的 Codex 和 Claude Code 里面就有”），用“我们”邀请读者一起看（“带着这个判断，我们重新看”）。

### 推销观点的心态（核心）

写作时心里有一个想说服的具体读者，带一点“推销观点”的心态——不是极端意义的推销，而是有意识地让读者接受你的判断。这是叙述感、对话感、说服感的根源。

有了这种心态：

- 文章像“把一段经历讲给一个读者听”，而不是“按顺序倒出自己的思考”；
- 主张明确、敢于坚持，每个判断都有说服意图；
- 自然出现“现在不能再怎么怎么”“大家现在要怎么怎么”“我建议你试试怎么怎么”“如果你也……不要……”；
- 读者能感到有人在跟他说话、想让他接受某个东西。

拉近读者的具体策略（原理，不是例句）：

- 用“我们”把读者拉进共同经历，让判断成为“我们共同的”（“这件事也提醒了我们一点”），而不是作者的个人笔记；
- 定义读者的处境，建立同类共鸣：“你和我一样正在尝试和学习 Loop、把 goal 用到任务里”——说教感随之消失，你不是在教，是在和同路人说话；
- 用“不要只……”“我建议你试试”直接面向读者劝诫。

判断问题：这篇文章读起来，是“作者在把一段经历讲给读者、想让他接受某个判断”，还是“作者在给自己做笔记”？
