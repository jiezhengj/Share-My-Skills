# 写作质量反馈与 Skill 自检

本文件处理一个元层问题：用户说“文章有 AI 味儿”时，除了文章本身，是否还在反馈编辑 Skill 的能力缺口。

## 一、何时触发

触发词不是机械关键词清单，而是入口信号。任何与写作质量有关的问题都需要至少一次轻量自检；以下情况通常需要完整自检：

- 用户直接说“AI 味儿”“很 AI”“不像人写的”“不像我”；
- 用户指出模板感、空泛、塑料感、客服腔、公文腔、强行升华、过度整齐或文章很顺但没有信息；
- 用户说标题、结构、结尾或语气不对；
- 用户连续否定改写结果，或询问为什么同类问题反复出现；
- 用户询问 Skill 是否真的有效、是否覆盖了某个最佳实践、是否需要增强；
- 用户提出局部措辞、标点或一般写作技巧问题，但需要先判断它是否暴露了可复用的 Skill 能力缺口。

孤立的措辞、标点或一般写作技巧问题执行轻量自检：说明文章层面怎么处理，说明是否发现 Skill 缺口，并询问是否要优化 Skill。只有当问题指向可重复的写作质量模式、整篇文章质量或 Skill 行为时，才需要更深入地讨论。这里的深浅是判断上的弹性，不是固定流程或必须完成的检查表。

## 二、如何判断真实意图

同时检查以下证据：

1. 用户这次明确说了什么；
2. 用户此前反复否定或强调了什么；
3. 当前文章或输出中是否存在对应现象；
4. 现有 Skill 是否已经规定了识别、处理和验收方式；
5. 用户是在要一篇文章、要解释原因，还是在要求修改 Skill。

不要把“我不喜欢这句话”扩大为“用户要修改整个 Skill”。也不要把用户对一次成稿的不满直接解释成 Skill 失效。只有当问题具有重复性、流程性或验收性，才提出 Skill 优化建议。

如需向用户说明判断，可参考下面的汇报格式；它不是固定模板，也不要求每次都填满：

```text
我的理解：你当前要解决的是……
依据：对话/文章中能看到……
仍不确定：我还不能确认……

文章层面的处理：……
Skill 层面的缺口：……
建议优化：……
影响范围：……

是否要同步优化 Skill？你确认后我再修改 Skill 本身。
```

## 三、讨论可能的优化时可以关注什么

如果确实判断存在 Skill 层面的缺口，不要只说“增强 Skill”“增加自然表达”。可根据案例酌情说明：

- **触发**：新增什么用户反馈入口，是否会误触发；
- **判断**：需要区分哪些文章问题和 Skill 问题；
- **流程**：在写前、写中、诊断或改写的哪个环节执行；
- **资源**：需要补充或调整哪份 reference；
- **动作**：要增加什么提问、改写动作或禁止动作；
- **验收**：如何证明以后遇到同类反馈会按新规则处理；
- **回归**：本次用户反馈如何成为测试案例；
- **范围**：是否影响脱敏、作者声音、事实回归或默认交付。

## 四、用户确认前后的边界

用户没有明确同意时，只能报告分析和方案，不修改 Skill 文件。可以按原有规则继续处理文章。

用户明确同意后，根据案例决定变更范围，再修改必要的 `SKILL.md`、reference、脚本或测试。若用户只同意处理文章，不应推断为同意修改 Skill。

脱敏仍是独立模块：用户提到写作质量或 AI 味儿，不会自动触发脱敏；只有用户主动提出脱敏、匿名化或隐藏身份信息时，才读取隐私模块。

## 五、回归记录

实际优化后，交付时说明与本次案例相关的：

- 这次反馈暴露了什么可重复问题；
- Skill 增加了哪条规则或资源；
- 哪个测试或验证证明规则已生效；
- 哪些事情仍然不能自动判断。

Skill 自检的目的不是让 Skill 无限扩大，而是把反复出现、可以复用的反馈沉淀成边界清楚的规则。
