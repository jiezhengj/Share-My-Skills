# macOS 与 Windows 兼容约定

- 文章、矩阵、报告和脚本参数使用路径对象或完整参数传递；不要手写平台分隔符，也不要假设用户目录、桌面或临时目录位置。
- 脚本统一按 UTF-8 读写。macOS 使用 `python3 -X utf8`；Windows PowerShell 使用 `py -3 -X utf8`（若系统只提供 `python`，再使用 `python -X utf8`）。带空格或非 ASCII 字符的路径始终加引号。
- Windows 下不要依赖 bash/zsh 的 `\\` 换行、`$VAR` 或 Unix 可执行权限；多步命令逐条运行，输出文件不要在编辑器或同步客户端中保持打开。
- 运行状态中的绝对路径只对生成它的系统有效；跨系统接续时从项目相对路径重新定位并重新运行初始化，不要直接复制另一系统的绝对路径。

把本 Skill 当作一套中文文章编辑流程，不当作 AI 作者身份检测器或“人类化滤镜”。目标是按原最佳实践的优先级，减少空泛、同构、模板化和语气失真，同时保留事实、判断、经验和文体。

# 先执行等价性约束

开始任何任务前读取 `references/coverage-matrix.md`。按矩阵确认本次任务覆盖了哪些诊断维度、需要哪些输入、应读取哪些 reference、哪些项目只能标记为 `UNKNOWN` 或 `NOT_APPLICABLE`。

将功能等价理解为：执行同一组判断和边界，不要求文字相同，也不承诺文章完全没有 AI 痕迹。未完成矩阵中的高优先级项目时，不声称“已经去除 AI 味儿”或“与最佳实践等价”。

# 写作质量反馈触发技能自检

当用户提出任何与写作质量有关的问题时，触发一次 Skill 自检，而不只是直接执行词句修改。重点信号包括：`AI 味儿`、模板感、空泛、塑料感、客服腔、公文腔、强行升华、过度平衡、不像作者本人、文章很顺但没有信息、结尾跑偏、结构不对、标题与核心判断不一致，或对当前改写结果明确表示不满意。也覆盖用户询问“怎样才能写得更自然”“为什么总有这些问题”“技能是否有效”等问题。

## bad case 原则

用户明确称为 bad case、指出结果不对，或质疑一个反复出现的问题时，把它当作需要理解的反馈，不当作立即新增黑名单、门禁或固定规则的指令。结合具体案例判断问题究竟出在哪里，是否只是当前文章的个案、是否可能反复出现，以及它主要属于本技能、`article-editor`，还是两者交叉；不要为了形成规则而强行归因。这里的检查是思考方向，不是固定流程、表格或标签。只有与用户讨论并确认后才修改技能；未确认时继续处理文章，或明确说明哪些判断仍待验证。

本技能优先审视抽象密度、模板化表达、句段形态、作者声音、过度自然化和误判风险；读者契约、文章身份、材料与作者意图、事实边界、结构和叙述逻辑，主要交给 `article-editor` 判断。两者有交叉时共同分析，不为了分工清楚而拆开真实的因果关系。

自检分两种深度：普通措辞、标点或局部表达问题执行轻量自检；涉及 AI 味儿、反复出现的问题、整篇文章质量或 Skill 有效性时执行完整自检。轻量自检也必须报告是否发现可复用的 Skill 能力缺口；没有发现时明确写出“当前未发现需要修改 Skill 的缺口”，不能静默跳过。

自检不等于固定流程或逐项填表；根据案例选择需要的上下文和证据，保持对根因、普遍性和技能归属的开放判断。

先区分两层问题：

- **文章问题**：当前文章的事实、内容、结构、语言、语气或作者判断哪里需要处理；
- **Skill 问题**：现有触发条件、工作流、参考文件、检查规则、改写动作或验收标准是否让类似问题反复出现。

根据当前对话和文件证据分析用户的真实意图。把结论分成“我的理解”“依据”“仍不确定”，不要把猜测写成用户已经确认的需求。然后在继续文章任务前或同时，向用户说明：

1. 对真实写作诉求的判断；
2. 当前表现的具体原因，以及它属于文章问题、Skill 问题，还是两者都有；
3. Skill 的具体优化方案，包括要改的范围、流程、reference、脚本/测试或交付规则；
4. 本次优化的优先级，以及是否会影响正在处理的文章。

使用清楚的一句收口：**“是否要同步优化 Skill？你确认后我再修改 Skill 本身。”**

在用户明确同意前：

- 不修改 `SKILL.md`、`references/`、`scripts/` 或 `agents/openai.yaml`；
- 可以继续完成当前文章的诊断或改写，也可以等待用户决定；
- 不把一次文章修订结果说成 Skill 已经修复；
- 普通写作技巧问题也先完成轻量自检，再直接回答；如果没有发现可复用的能力缺口，明确说明原因，不把它夸大成需要修改 Skill 的问题。

用户明确同意后，根据案例决定是否需要修改 Skill；如果修改，先说明变更范围和如何判断有效，再修改必要的 Skill、测试或 reference，并进行相称的验证。完成后把本次反馈作为一个 Skill 回归案例记录在交付说明中。

如果当前反馈已经被现有规则覆盖，且对应回归案例通过，报告 `NO_GAP_FOUND`，继续处理文章，不为了“还可以更好”而开启新一轮 Skill 修改。只有出现新类型问题、现有规则与用户要求冲突，或回归测试失败时，才重新提出 Skill 优化。

# 不可违反的边界

- 不根据单个词、单一检测器分数、语法流畅度或标点规范判断作者是否使用 AI。
- 不把“AI 率”当作 AI 生成比例，不计算总风险分数。
- 不为了“像人”添加错别字、随机断句、口头赘词、虚假情绪或不必要的不规则。
- 不编造作者经历、案例、数字、引用、来源、失败过程、现场细节或因果关系。
- 不把个人经验扩大成普遍规律；区分事实、经历、观察、推断和建议。
- 不把正式报告、技术文档或结构清楚本身当作 AI 味儿。
- 不在用户未授权时覆盖目标文章或创建第二个最终版本。
- 用户没有明确要求脱敏时，不询问、不扫描、不替换身份信息，不读取隐私模块。

# 选择模式和任务标志

| 模式 | 进入条件 | 默认交付 |
| --- | --- | --- |
| `prewrite` | 只有主题、素材、口述或写作计划 | 读者契约、素材地图、中心判断、提纲和风险预警，不写完整正文 |
| `drafting` | 用户确认前置简报并要求写作 | 按小节写作并执行 checkpoint |
| `diagnose` | 用户只要求评估已有文章 | 诊断报告，不修改目标文件 |
| `rewrite` | 用户明确允许改写已有文章 | 按最低必要等级改写并回归事实 |
| `cold-read` | 用户要求陌生读者检查或文章已修订 | 冷读报告和剩余问题 |

使用 `privacy_opt_in = false` 作为默认值。只有用户明确说“脱敏、匿名化、隐藏项目名/路径/账号”等，才设为 `true`，读取 `references/optional-privacy-module.md`，并在交付说明中报告脱敏变更。

用户只说“润色”时，先确认是准确性、可读性、作者声音、结构、减少模板感，还是其他目标；不要默认执行最高强度改写。

# 建立编辑简报

先确认：

- 目标文件或原始素材路径；
- 写作阶段和文章类型；
- 目标读者、发布场景和文章承担的判断；
- 是否允许直接改写原文件；
- 必须保留的事实、数字、术语、引用、原话、标题、图片和内部链接。

不要主动询问脱敏。只有用户已明确提出时，才设置 `privacy_opt_in = true`。

形成以下读者契约：

```text
这篇文章写给谁？
读者在什么情况下需要它？
文章准备处理什么问题？
读者读完后能做什么、判断什么或记住什么？
文章明确不承担什么判断？
```

为重要材料标记：

| 标记 | 含义 |
| --- | --- |
| `FACT` | 可核验事实、数字、引用或时间 |
| `EXPERIENCE` | 作者亲自经历或操作过的内容 |
| `OBSERVATION` | 作者或来源观察到的现象 |
| `INFERENCE` | 根据材料做出的推断 |
| `RECOMMENDATION` | 给读者的建议 |
| `UNKNOWN` | 缺少信息或尚未确认 |

缺少会改变文章结构或事实边界的信息时，第一轮最多提出 3–6 个高价值问题。用户不回答时保留 `UNKNOWN`，不顺滑补齐。

# 执行写前和写中流程

## `prewrite`

1. 读取素材，不先生成完整文章。
2. 建立 `reader-contract`、`source-map`、`claim-ledger` 和素材关系图。`source-map` 还要记录每条材料的来源权限：哪些是可直接写成作者事实的原文，哪些只能写成观察、推断、假设或 `UNKNOWN`。
3. 找出真实起点、冲突、转折、失败、结果或未解决问题。
4. 先标记 `trajectory_mode`：
   - `ENABLE`：文章核心在讲作者或参与者如何在不确定中理解、行动、遇到阻碍、修正判断，或方法如何从一段实践中长出来；
   - `SKIP`：纯技术文档、产品说明、纯观点文或只报告最终结果；
   - `UNKNOWN`：材料不足以判断，先不加载过程问题，也不顺滑补写认识变化。
   只有 `ENABLE` 才读取 `references/process-and-stop.md`，记录原本的预期、行动、观察、局部成功、整体是否推进、成本、停止或转向和判断变化。路由依据文章的叙述形态，不依据是否出现 Agent、Workflow 等主题词。对于 `ENABLE` 的项目复盘，额外检查“项目经历履历化/报告化”：阶段标签只能提供时间顺序，不能代替每个阶段的具体对象、动作、观察结果或判断变化。
5. 找出案例、概念、读者疑问和判断之间的关系：哪个案例提出问题，哪个概念解释它，哪个结果改变理解，后面的建议回答什么疑问。
6. 根据材料形成结构，不默认套用“背景—问题—对策—展望”或三点清单。
7. 标出中心判断、支撑材料、反例、取舍、适用边界和未知项。
8. 输出提纲和风险预警，等待用户确认后进入写作。

前置停止标准：读者、问题、中心判断和结构方向清楚；缺失材料已标记；作者知道下一步写什么。

## `drafting`

按小节推进。每节都：

1. 只读取当前小节需要的素材；
2. 写出具体对象、动作、时间、结果或判断；
3. 检查抽象概念是否落到已有的对象、动作、结果、反例或限制上；
4. 如果已启用“判断轨迹与过程收口”模块，检查是否保留了局部成功与整体结果之间的差异；
5. 检查是否把推测、假设案例或外部资料写成作者亲身经历；
6. 检查作者声音、术语边界和证据强度；
7. 记录 checkpoint 后再继续。

禁止为了段落匀称补第三个例子，禁止为了结尾完整改变中心判断，禁止把材料缺口包装成展望。

# 执行成稿诊断流程

按以下顺序检查，并为每一项记录 `FOUND`、`CLEAR`、`UNKNOWN` 或 `NOT_APPLICABLE`：

1. **硬证据**：提示词残留、模型免责声明、占位符、虚构引用、无法解释的精确数字、事实冲突、时间线冲突、跨文章重复。读取 `references/ai-flavor-signals.md`。
2. **内容证据**：事实可核查性、来源与论点匹配、信息密度、机制、案例、反例、取舍、原创观察和可反驳判断；仅当 `trajectory_mode = ENABLE` 时，再检查局部成功、整体推进、成本和停止事件。读取 `references/content-and-claim-audit.md`，需要时再读取 `references/process-and-stop.md`。
3. **具体性与作者感**：不可替换的经历、动作、后果、异常细节、情绪与事件是否匹配、术语是否准确、地域或文化细节是否只是符号；区分承担事实和判断的第一人称，和只负责报幕的第一人称。需要时读取 `references/author-voice.md`；对个人文章或复盘类成稿，再读取 `references/human-narrative-shape.md`，检查命名密度、升华密度、否定对仗密度、情绪缺席和氛围性细节。
4. **读者路径**：文章是否让读者看到原先的理解、遇到的阻碍、判断为什么改变，以及后面的例子或方法如何回答前面的疑问。正式报告和技术文档可以直接给结论；面向读者的文章读取 `references/reader-facing-narrative.md`。
5. **结构信号**：段落同构、三点清单、重复总结、强行开场、结尾拔高、标题模板化、同义复述和低信息量的作者自述型过渡。读取 `references/rewrite-patterns.md`。
6. **语言信号**：抽象名词、泛比喻、机械连接词、对称句、空泛评价和匀速句式。读取 `references/ai-flavor-signals.md` 和 `references/rewrite-patterns.md`。
7. **统计与发布上下文**：句长/段长波动、重复、情绪词、模板密度、跨文章重复、批量发布和主题跨度。只有输入提供相应上下文时才检查；读取 `references/quantitative-and-publishing-signals.md`。
8. **误判边界**：对照 `references/false-positive-boundaries.md`，确认正式文体、教学引用、采访原文或技术结构没有被错误改写。

**对向检查（写作质量是双向的）**：除上述单向信号外，同时检查两个反向，并为每一项记录 `FOUND`/`CLEAR`：

- **去味过头 / 表演人味**：短句断言堆砌、口语词装饰但删掉后无信息增量、为自然牺牲具体性、伪情绪（假装情绪波动但不敢写足，情绪词张冠李戴，删掉后论点不变即假情绪）。
- **工整论文感**：段落对称、每节收束句无新增信息、自我声明式开场（“结论先放在这里”）、“不是…而是…”对仗句密度、时间锚点缺失、句句笃定无犹豫。
- **上价值机制**：洞察前置（第一段透支结论）、意义通胀（把具体经历的意义说大）、元话语组织句失真（“放在这里”“这里需要”“值得记下来”）、伪转折/伪揭示（“其实”“X 并不是从 Y 开始的”）、空转叙述支架（“一开始”“这一次”）、空转限定词（“基本”无实指）、悬空指向词（“这”“这里”“别处”等没有可识别参照）、无出处比喻（“那面墙”）、廉价强度词（“真正”“逼出”）、防御性自证（回应幻影指控）、回顾渲染（“回头看”随机贴标签）、标题失真（“真正的X，不是Y”）。
- **元原则：信息浓淡错位**——该精简的地方不精简（填充词、元话语、伪转折、收束句、金句），该展开的地方又太精简（真实场景、因果机制、关键时刻、具体数字）。对向检查同时纠正两个方向。

以上完整组合信号与形态样本见 `references/ai-flavor-signals.md` 的“对向检查”章节。

无法核验引用、数字、发布行为、地域事实或作者意图时标记 `UNKNOWN`，不能写成 `CLEAR`。没有提供发布上下文时标记 `NOT_APPLICABLE`，不能解释为账号行为正常。

# 执行分层改写

选择最低必要等级：

- `L0`：只报告问题，不改写；
- `L1`：清除提示词残留、占位符、重复和无信息句；
- `L2`：调整读者路径、术语解释、段落顺序和重复结构；
- `L3`：仅根据作者补充材料增加过程、失败、反例、限制和取舍；
- `L4`：处理抽象词、模板句、泛比喻、节奏和过度正式表达。

先处理硬证据和内容问题，再处理结构和语言。不要先做全局同义词替换。事实、结论、原话和术语发生变化时，在交付说明中逐项列出。

语言层（L4）只处理表达，**不得删除事实、数字、案例、因果、具体物件/动作**；若发现信息不足，标记 `UNKNOWN` 并回到 `prewrite` 或交给老编辑（材料与意图边界），不用口语填充。

处理经验型或混合型文章时，先恢复“情况/疑问 → 阻碍或反例 → 判断变化 → 方法或建议”的关系，再处理句子。没有对应素材时标记 `UNKNOWN`，不靠口语、比喻或虚构场景填补。

形态问题（命名密度、金句式升华、否定对仗成串、情绪缺席、氛围性细节）只能用作者材料解决；识别出形态问题但材料不足时标记 `UNKNOWN` 并回到 `prewrite` 或提问，禁止用换词、加氛围细节、自报情绪或造对话腔来表演人类。作者原话中已有人味的句子保持不动。

处理项目复盘时，增加一项“履历化/报告化”门槛：如果连续多个阶段只按“阶段状态 → 执行动作 → 成果归纳”展开，且读者无法说出每个阶段独有的对象、动作、观察或判断，改写不得只做换词和顺句。回到 `source-map`，保留作者原话、术语、概念词和限定判断；材料不足时压缩、追问或标记 `UNKNOWN`。

处理第一人称时，保留能证明作者做过什么、看到什么、如何判断或承担什么责任的“我”；合并或删除只表示“接下来我想到/我觉得/我于是/我现在会”的叙述支架。不要按“我”的数量机械删改，也不要把文章改成无作者的说明书。

做原话回归时，不得把“听起来像模型”的词语当作模型新增内容。先确认它是否出现在作者原始材料中；作者原话可以凝缩、正式或带专业术语，来源明确时应保留，不得擅自口语化或替换。

处理已启用过程模块的文章时，不要把“每一步做对了”写成“整体取得进展”。保留局部成功、整体无进展、时间或 token 等实际成本，以及作者为什么继续、何时停止和依据是什么；如果材料没有提供停止依据，标记 `UNKNOWN`，不要补写一个漂亮的收口。Agent、Goal 或 Workflow 只是这类过程的例子，不是模块的触发条件。

对项目复盘，避免连续使用阶段标签、清单式工具名和成果归纳替代叙述推进。每个主要阶段至少落到一个来源明确的对象、动作、结果或判断；材料不足时压缩、追问或保留 `UNKNOWN`，不得补写。来源明确的作者术语、概念词、比喻和带限定的判断可以保留，即使它们不口语化或较为凝缩。

改写后执行事实回归和 `cold-read`：

1. 读者是谁？
2. 文章处理什么问题？
3. 作者的中心判断是什么？
4. 读者读完后能做什么或判断什么？
5. 是否新增了作者没有提供的事实、例子、因果、来源或数字？
6. 如果是项目复盘，读者能否说出每个主要阶段独有的对象、动作、观察结果或判断变化？如果替换项目名和工具名，段落是否仍然可以移植？作者原话是否被准确保留？

前四题不能回答，或第五题答案为“是”时，不得交付为完成。

# 可选脱敏模块

仅当用户主动触发时读取 `references/optional-privacy-module.md`。保留动作、过程、结果和限制，只替换身份、项目、路径、账号、仓库和设备信息；如果证据减弱，降低结论强度。

用户没有主动提出脱敏时，跳过本节，不在诊断报告中加入隐私检查项。

# 等价性和交付门槛

只有在以下条件同时满足时，才将本次处理标记为 `EQUIVALENT`：

- 矩阵中的相关高优先级项目都有检查结果；
- 未把 `UNKNOWN` 当作通过；
- 原最佳实践要求的证据顺序已执行；
- 相关 reference 已读取，脚本已运行或说明无法运行；
- 没有新增虚构事实、引用、数字、经历或因果；
- 正式文体、技术文章或自然文章没有因“像 AI”而被强行口语化；
- 用户未请求脱敏时隐私模块未触发；
- 完成冷读、事实回归和剩余风险说明。

任意高优先级项目缺失或反向测试失败时，标记为 `PARTIAL`，不要使用“基本等价”。交付说明至少列出：当前模式、改写等级、已检查项目、`UNKNOWN`、`NOT_APPLICABLE`、实际修改、保留内容和剩余风险。不要声称“已经去除 AI 味儿”。

本轮叙事质量优化的封口条件是：已区分文档与面向读者的文章，已定义素材来源权限，已规定案例—概念—判断关系、读者代理和判断轨迹；过程收口规则已按文章形态接入写前、诊断、改写和冷读流程，而不是绑定某个主题。封口时执行以下可复现检查：

- macOS：`python3 -X utf8 <skill-dir>/scripts/test_skill_contract.py`；
- Windows PowerShell：`py -3 -X utf8 <skill-dir>/scripts/test_skill_contract.py`；
- macOS：`python3 -X utf8 <skill-dir>/scripts/validate_coverage.py <skill-dir> --format json`；
- Windows PowerShell：`py -3 -X utf8 <skill-dir>/scripts/validate_coverage.py <skill-dir> --format json`。

四条命令均成功且覆盖矩阵无错误后，后续同类反馈先报告 `NO_GAP_FOUND`；只有新失败案例或规则冲突才开启下一轮 Skill 修改。
