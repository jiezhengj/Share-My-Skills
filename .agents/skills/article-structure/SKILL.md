# 执行职责

执行一次保真的结构编辑：先理解文本自身的阅读方式、内容关系、节奏和可能的版式意图，再以最小必要干预改善读者的理解与定位。不得把所有文本整理成同一种说明文版式，不以标题数量、段落数量或视觉整齐作为完成标准。

# 输入与输出路由

先识别文章来源和用户本次明确指定的输出方式；用户指定优先于默认规则。

| 来源 | 默认输出 |
| --- | --- |
| 本地 `.md` / `.markdown` | 原地更新同一文件 |
| 飞书 Docx/Wiki | 直接写回原飞书文档 |
| 项目 `source-ref.json` | 使用引用的只读 `source.md`，在运行目录编辑 `structured.md`，默认写回引用中的原飞书文档 |

- 用户可明确指定另存本地路径或创建副本；否则飞书 URL/token 或 Feishu `source-ref.json` 一律更新原文，不创建“结构梳理”副本。
- 飞书来源但要求本地输出、且未给本地路径时，要求用户提供路径。不要擅自选择目录。
- 如果输入是飞书 URL/token，必须先把完整 Markdown 保存到当前工作区的 `.feishu-sources/<document_id>/revisions/<revision_id>/source.md`，并保存 `source-meta.json`；来源快照写入后再进行结构分析。
- 如果输入是项目 `source-ref.json`，先验证来源路径和 SHA-256，直接读取其中的 `source.md`，不得再次抓取原文；写回时使用其中的 `source_url`，不重新探测 revision。
- 标准来源 `source.md` 只读；结构梳理只能修改它的运行目录副本 `structured.md`。项目已提供 `tools/feishu_source_snapshot.py` 时，URL 抓取必须使用该工具。
- 活动工作区没有来源工具时，也必须按同一固定目录原子写入 `source.md`、`source-meta.json` 和 `current.json`；同一 `document_id`/`revision_id` 已存在时先比对 SHA-256，相同则复用，不同则停止，绝不覆盖既有 revision。所有路径仍从任务初始 cwd 的 Git 根推导，不从本技能真实目录推导。
- 飞书写回保持原文档标题不变，不新增“｜结构梳理”后缀。
- 处理飞书前，先用 `lark-cli skills read` 加载 `lark-shared`、`lark-doc` 及对应参考说明；默认显式使用 `--as user`。读取、写回和回读按当前 `lark-doc` 指引执行。

# macOS 与 Windows 运行约定

- 从用户发起任务时的初始 cwd 执行 `git rev-parse --show-toplevel`，把返回的绝对路径固定为 `workspace_root`；不要从本技能目录、软链接真实目录或脚本 `__file__` 推导工作区。
- Python 启动器按系统选择：macOS 使用 `python3`；Windows 优先 `py -3`，不可用时使用 `python`。不要依赖 Windows 的 Microsoft Store `python3` 占位入口；本技能校验脚本只使用 Python 标准库。
- Bash 示例中的 `\\` 只是续行符。PowerShell 请改成单行命令或使用反引号；所有路径加引号并交给 `pathlib` 处理，来源 JSON 中的相对路径统一使用 `/`。
- 所有 Markdown、JSON 和快照文件显式按 UTF-8 读写。Windows 不要把 lark-cli stdout 通过 PowerShell 原生管道直接交给中文校验脚本；先用项目共享来源快照工具保存，再读取本地 `source.md`。macOS 也遵循同一来源快照契约。
- 飞书 CLI 必须由外层终端调用。macOS 使用 PATH 中解析出的 `lark-cli`；Windows 依次检查 `Get-Command lark-cli`、`where.exe lark-cli` 和 npm 全局目录中的 `lark-cli.cmd`，必要时保存绝对 `.cmd` 入口，避免 `npm.ps1` 执行策略问题。
- 本技能可以由项目外部技能注册或软链接直接加载；不要假设调用方必须在项目内创建软链接，也不要从本技能真实目录推导 `workspace_root`。软链接调用时仍从任务初始 cwd 定位 Git 根和输入/输出文件。

## macOS 沙箱前置

- 输入是飞书 Docx/Wiki URL 或 token 时，第一次访问飞书前必须直接在沙箱外执行当前工作区的来源快照命令；不要先在普通沙箱里试跑再等待 Keychain 失败。
- `lark-cli` 读取已配置的 macOS Keychain 身份时，沙箱内可能直接返回 `keychain Get failed: keychain not initialized`。这只是执行环境限制，不是文档不存在、权限不足或需要重新登录的结论。
- 将下面飞书文档工作流中的 `python3 tools/feishu_source_snapshot.py fetch ...` 作为一次只读的外部命令启动；命令成功写入 `source.md`、`source-meta.json` 和来源引用后，才能继续结构分析。
- 本任务后续所有会访问飞书的 `lark-cli` 命令（包括写回和回读）也必须继续在沙箱外执行；不要只把首次抓取放到外部。
- 如果外部执行仍返回明确的认证/权限错误，再按 `lark-shared` 处理；不要因沙箱 Keychain 错误改用浏览器抓取或重复探测。输入已经是 `source-ref.json` 时直接验证并复用，不访问飞书。

# 运行兼容性

- 由 Agent 的外层终端直接调用 `lark-cli`；不要在 Node.js、Python 或其他临时子脚本中以裸命令 `lark-cli` 启动飞书 CLI。
- Windows 下先按顺序检查 `Get-Command lark-cli`、`where.exe lark-cli`、`npm.cmd prefix -g` 对应的 `lark-cli.cmd`。若 PowerShell 命中 `npm.ps1`，改用 `npm.cmd` 或 `lark-cli.cmd`；不要依赖执行策略允许 `npm.ps1`。
- 将解析出的绝对入口保存为变量再调用，例如 `$LarkCli = 'C:\\Users\\<用户名>\\AppData\\Roaming\\npm\\lark-cli.cmd'`，并显式传 `--as user`。除非用户明确要求应用身份，否则不得改用 `--as bot`。
- 如果 user 授权失效或缺少 scope，按 `lark-shared` 的 split-flow 重新发起授权；不得静默切换为 bot。
- PowerShell 原生管道可能把 lark-cli 的 UTF-8 JSON 变成 `?`。需要把飞书内容交给 Python 校验脚本时，先用字节安全的抓取器或保存为 UTF-8 文件；禁止直接把原生 PowerShell 管道接入依赖中文的临时脚本。
- 临时脚本只接收已抓取的 Markdown / XML 文件或标准输入；不要让它们自行抓取飞书文档。飞书读取、创建与回读均留在外层终端步骤。
- 本技能新增的校验脚本必须只依赖 Python 标准库。缺少可选工具依赖（例如 `PyYAML`）时，使用本技能的便携自检；不要为一次文章整理临时安装依赖。

# 文档标题与正文层级

飞书的**文档标题**与**正文标题**是两套互不占位的结构，所有标题判断先遵守本节。

- 按此顺序确定文档标题：飞书 / 文件元数据标题 → YAML frontmatter 的 `title` → 开头唯一 H1。后两者仅用于补足元数据，不自动成为正文标题。
- 文档标题只写入飞书 `<title>`（或本地文件名 / frontmatter 的 title 字段），**绝不占用正文 H1–H4 层级**。
- 正文第一个实际章节必须是 H1；所有并列的一级章节也必须是 H1。只有从属于某个一级章节的内容才能使用 H2，再依次使用 H3、H4。
- 禁止因为全文标题存在，就把真正的章节标题统一降为 H2；禁止出现“正文只有一个全文标题 H1，而所有实际章节从 H2 开始”的结构。
- 来源 Markdown 开头若有唯一 H1，且其文字与文档标题相同（忽略“｜结构梳理”后缀），它是文档标题元数据，不是正文内容：写回原飞书文档时保留其文档标题语义，**不再写成正文标题块**。这不是删除正文。
- 仅当原有 H1 确实是正文中的一级章节时，才保留其文字并维持为正文 H1。
- 当无法可靠判断开头 H1 是文档标题还是正文一级章节时，优先将其视为文档标题元数据；不要让不确定的标题占据正文 H1。
- **开篇引子允许无标题**：正文开头若属于作者与读者建立共鸣、抛出问题或叙述背景的漫谈与引子（Hook / 前言铺垫），允许且鼓励开头保留无标题的连续阅读流，**严禁强行给开篇引入部分安放概括性标题**。正文的第一个实际章节（H1）应落在核心正题真正开始展开的位置。

# 保真边界与作者阅读契约

保留正文的所有文字、标点、数字、链接、引用、案例、代码、图片、表格和内容块顺序。不得改写、润色、删减、扩写、调换或合并原文内容。

原文段落边界属于需要理解的材料，不是绝对不可触碰的边界：允许在完整句子或明确的语义/节奏边界处把一个源段拆成多个显示段落，但不得改变段落内部文字顺序，也不得把原本独立的源段合并。拆分、保留或不加标题都必须服务于文本自身的阅读方式。

只允许以下结构动作，且没有哪一种动作对所有文本都必需：

1. 新增基于原文的 Markdown 标题；标题只概括对应内容，不添加原文未表达的观点、承诺或信息，且必须严格遵守下述“标题拟定与语态契合原则”。
2. 调整现有**正文**标题的 `#` 层级，不改标题文字。每个一级章节使用 H1，并在其下依语义使用 H2、H3、H4；不得将文档标题作为正文 H1。
3. 在有充分文本证据的边界处拆分段落。不要用固定句数、字数或题材规则代替判断，也不要为了整齐拆散紧密的论证、引文、意象、节奏或刻意的密度。
4. 审慎使用 Markdown 加粗，突出原文已有且对定位有帮助的关键内容；只添加 `**` 标记，不改动被标注的文字。
5. 仅当原文已有清楚的并列关系、且列表或表格不会改变原文的语气和阅读关系时，整理为列表或表格；无法无损转换时保持原段落。

## 标题拟定与语态契合原则

- **语态随文，尊重作者原声**：标题语态必须跟随文本体裁和作者原声。在个人博文、实战心得或对话感强的文章中，标题应保持第一人称或平视读者的口吻，直接提供心理预期与情绪正反馈（如“实现超简单”、“做了个锦上添花的技能”）；严禁把所有文本标题都写成冰冷刻板的第三方规格说明。
- **杜绝工程化大词与公文套话**：严禁在非纯技术规范的文稿中生成“落地实现”、“真实工况”、“封装为……”、“……之方案及其局限”等生硬模板词；优先使用口语化、穿透力强的业务白话（如“场景”、“优势”）。
- **提炼单一核心抓手，拒绝要素穷举**：标题只提供该章节最核心的一个视觉锚点，不承担全文信息覆盖责任。严禁把章节内的多个并列工具、技术参数或从句强行用连词拼凑成复合长标题（如“A 与 B 的契合优势及 C 的扩展”）；把细节和技术参数留给正文交付。

## 判断原则

- 把文本视为有作者意图的阅读对象，而不是待套用模板的内容集合。段落可能承载论证，也可能承载叙事推进、情绪变化、语气停顿、意象连续性、视觉重量或刻意制造的压迫感。
- “更易扫读”是条件性目标，不能凌驾于作者的表达方式和阅读效果之上。长段不必然需要拆，短段也不必然需要合并；先判断它在文本中发挥的作用。
- 识别来源格式造成的偶然边界与作者有意保留的边界。判断依据来自全文及局部关系、重复与平行、转折、语气、标点、既有空行和内容推进的综合证据，不来自单个关键词。
- 对重复、平行或同位的内容建立“关系组”整体判断。关系组的成员可以是分项、回应、例证、场景或情绪段落，不以编号、句式或固定词语作为识别条件。一个成员的段落、标题、列表或强调方式发生变化后，必须回看同组其他成员；除非有明确的语义、节奏或视觉证据，否则不能让同一关系组出现部分规范化、部分未处理的版式。
- 分辨引导语、总述、过渡与关系组第一个成员各自承担的功能。若引导语和第一个成员职责不同，而后续同类成员已被独立呈现，应评估是否需要把二者分开；若整组内容本来依靠连续语流、压迫感或诗性推进，则保持整组连续。不能仅因来源恰好把二者放在同一源段，就放弃关系层面的判断。
- 把空行及连续空行视为版式和语气的一部分，而不是可以无条件忽略的空白。结合空行所在位置、连续长度、前后语义、全文重复模式和阅读节奏，判断它是停顿、留白、转场、情绪强调，还是导出/编辑造成的孤立残留。异常空行只有在缺少文本功能且与全文模式不相称时才应被合并；不要用“空几行就一定错误”的固定阈值替代判断。
- 当一个候选改动既可能改善理解，也可能破坏节奏，而文本没有足够证据表明哪一种更符合作者意图时，采用更少干预的方案。
- 不要把某一次文章中的结构发现提升为跨题材规则。任何示例都只是说明如何推理，不是必须触发的模式。

## 先建阅读模型，再编辑

通读全文，在内部形成一个面向当前文本的阅读模型，不写入最终文章，也不必套用固定分类。至少判断：

1. 文本希望读者如何阅读：快速定位、连续聆听、沉浸叙事、情绪推进、反复咀嚼，或多种方式并存。
2. 每个内容块在当前上下文中的作用，以及它与前后内容的关系：引入、展开、转折、回声、例证、停顿、收束等只是可能性，不是预设模板。
3. 哪些内容构成语义上的关系组；组内成员的边界、标题、列表和强调是否相互照应，是否存在第一个成员与引导语粘连而后续成员独立等关系性断裂。
4. 现有标题和空行哪些是在揭示结构，哪些可能只是来源格式；尤其检查连续空行的长度、位置和全文中的孤立异常，判断新增或删除边界会增强还是削弱语义、节奏和视觉效果。
5. 哪些结构判断是高置信度，哪些仍然存在多种合理解释。只对高置信度且有明显收益的地方做结构干预。

对每个候选拆分或标题，先做一次反事实检查：如果保留原样，读者会误解结构还是只是阅读更连续？如果拆开或加标题，是否会把有意的连续性、含混、压迫感或诗性抹平？选择能够解决实际问题且最少改变阅读体验的版本。

## 编辑顺序

1. 先完成阅读模型和结构地图，再决定是否需要结构动作；不要因为技能支持标题、分段、加粗、列表和表格，就把它们全部使用一遍。
2. 对每个关系组先做整体版式决策，再处理其中的局部边界；如果只改变了一个成员，必须确认差异确实由文本功能造成，而不是处理遗漏。
3. 先处理影响理解或定位的高置信度边界，再处理标题层级和局部强调；没有明确收益的段落保持原样。
4. 单独复核空行的视觉功能：保留有上下文支持的留白，修复高置信度的孤立异常，并检查调整后是否破坏了全文的节奏模式。不要把空行审查交给只比较正文文字的脚本。
5. 比较“少干预”和“较多干预”的结果，选择更符合当前文本阅读契约的版本。不要追求固定的标题数量、段落数量、平均段落长度或统一的空行数量。
6. 交付前从头到尾复读结构稿，重点检查开头、结尾、重复结构组、关系组成员之间的版式一致性，以及突然出现的异常空白。确认版式仍然像这篇文本，而不是像某种通用的说明文模板；确认所有新增结构都能在原文找到依据。

## 语义判断与脚本校验的分工

文本类型、作者意图、节奏、段落边界和标题是否破坏语气，必须由 LLM 结合全文判断。脚本只负责确定性不变量：正文文字与顺序、链接和内容块、标题层级、文档标题元数据及文件格式。通过保真脚本不代表版式判断已经正确，也不得用脚本的固定阈值替代文本理解。

# 来源快照与本地 Markdown 工作流

1. 普通本地 Markdown 输入：将原文件复制为临时原文快照，建立临时修订稿和“新增结构行”JSON 清单。项目来源快照输入：从标准 `source.md` 复制为运行目录的 `structured.md`，不得覆盖来源文件。清单为 JSON 数组，记录所有新增标题、表头与分隔行，例如 `["## 核心步骤", "| 项目 | 说明 |", "| --- | --- |"]`。
2. 根据结构地图在临时修订稿完成最小必要的整理，运行 [verify_preservation.py](scripts/verify_preservation.py)。macOS 使用 `python3`，Windows PowerShell 使用 `py -3`（不可用时用 `python`）：

   ```text
   macOS:
   python3 scripts/verify_preservation.py \
     --source <原文快照> --revised <临时修订稿> \
     --generated-lines <新增结构行清单.json> \
     --document-title "<文档标题>"

   Windows PowerShell:
   py -3 scripts/verify_preservation.py `
     --source <原文快照> --revised <临时修订稿> `
     --generated-lines <新增结构行清单.json> `
     --document-title "<文档标题>"
   ```

3. 校验失败时修订临时稿；不得通过删掉校验、放宽比较或忽略错误来交付。
4. 校验通过后，用 `apply_patch` 将同样的变更写回原 Markdown；回读最终文件并再次运行校验。
5. 若文档有标题元数据，运行 [verify_heading_structure.py](scripts/verify_heading_structure.py)：

   ```text
   macOS:
   python3 scripts/verify_heading_structure.py \
     --markdown <最终正文 Markdown> --document-title "<文档标题>"
   Windows PowerShell:
   py -3 scripts/verify_heading_structure.py `
     --markdown <最终正文 Markdown> --document-title "<文档标题>"
   ```

   校验“第一个正文章节为 H1”及“文档标题未被写成正文 H1”。

# 飞书文档工作流

1. 对飞书 URL/token 输入，先使用当前工作区定义的来源快照工具完整抓取并保存标准 `source.md`；对 source-ref 输入直接使用其已验证的 `source.md`。先识别并剥离文档标题元数据，再按相同保真边界完成结构地图、运行目录中的 `structured.md` 与新增结构行清单。不得在此阶段重新抓取原始飞书文档。
2. 在写回原飞书文档前运行完整性校验与 [verify_heading_structure.py](scripts/verify_heading_structure.py)。校验通过后，使用 `docs +update --command overwrite --doc-format markdown` 将 `structured.md` 写回原文档，保持原文档标题不变。该项目已接受整篇 overwrite 可能影响图片、评论或复杂嵌入块的风险。
3. 回读原文档，核对标题层级、段落与列表/表格顺序、链接和内容完整性。回读内容应再次运行 `verify_heading_structure.py`：第一个正文章节必须是 H1，且不能有与文档标题等同的正文 H1。任一标题门禁失败，修正后再交付。飞书 Markdown 往返可能调整纯格式，因此以写回前的完整性校验保护正文，以回读核对内容与结构。

# 交付

- 本地来源：报告已更新的原文件路径。
- 飞书来源：报告原文档 URL、标准 `source.md` 路径、来源 `document_id`、`revision_id` 和 SHA-256。
- 如用户要求引言、总结、SEO 文案、改写或段落重排，先明确该项将突破默认保真边界；只在用户确认后执行。
